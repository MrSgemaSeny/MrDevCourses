## 1. Что такое Full-Stack на самом деле (Ментальная модель)

Многие думают, что веб-приложение — это просто красивая страничка в браузере. На самом деле любое промышленное приложение состоит из трех изолированных независимых частей:

```text
+-----------------------+        HTTP / JSON         +-----------------------+        SQL / TCP          +-----------------------+
|       ФРОНТЕНД        | -------------------------> |        БЭКЕНД         | ------------------------> |      БАЗА ДАННЫХ      |
|     (React 19)        | <------------------------- |    (Spring Boot 3)    | <------------------------ |     (PostgreSQL)      |
|  Браузер пользователя |        Ответы API          |   Сервер и логика     |        Таблицы            |   Надежный сейф       |
+-----------------------+                            +-----------------------+                           +-----------------------+
```

### Аналогия с рестораном:
1. **Фронтенд (Зал ресторана и меню):** То, что видит гость. Красивый стол, кнопки, формы, диаграммы. Сам по себе фронтенд еду не готовит и продукты не хранит. Если закрыть браузер, на компьютере клиента ничего не остается.
2. **Бэкенд (Кухня ресторана):** Скрыт от глаз клиента. Здесь работают повара (бизнес-логика). Они проверяют: оплатил ли гость заказ, есть ли у него аллергия, свежие ли продукты. Бэкенд решает, можно ли выполнить действие.
3. **База данных (Кладовая со складом):** Полки с пронумерованными коробками. Там лежат сырые данные: сколько денег на счету, пароли, списки покупок. Доступ в кладовую имеют только повара (бэкенд). Гостя туда никогда не пускают.

> **Главное правило безопасности:** Фронтенд НИКОГДА не общается с базой данных напрямую. Если бы браузер мог сам писать в базу, любой пользователь через консоль разработчика (F12) мог бы нарисовать себе миллион долларов на балансе. Любое действие всегда проверяет бэкенд.

## 2. База данных (PostgreSQL): Надежный сейф данных

База данных — это не просто файлы на диске. Это специализированная система, которая гарантирует: если сервер внезапно выключится из розетки, ни один цент не пропадет.

### 2.1. Реляционная модель: Таблицы и связи
В проекте «Трекер денег» данные хранятся в реляционной базе **PostgreSQL**. Слово «реляционная» означает, что таблицы связаны между собой через ключи:

1. **Таблица `users` (Пользователи):**
   * `id` — уникальный номер (Первичный ключ / Primary Key, PK);
   * `email` — электронная почта;
   * `password_hash` — зашифрованный пароль;
   * `role` — роль (`STUDENT` или `ADMIN`).

2. **Таблица `categories` (Категории расходов):**
   * `id` — номер категории (PK);
   * `name` — название (Еда, Жилье, Транспорт, Подписки);
   * `color` — HEX-код цвета для графиков.

3. **Таблица `transactions` (Операции с деньгами):**
   * `id` — номер транзакции (PK);
   * `user_id` — чей это расход (Внешний ключ / Foreign Key, FK на таблицу `users`);
   * `category_id` — какая категория (FK на `categories`);
   * `amount` — сумма (в центах или с плавающей точкой);
   * `created_at` — точное время операции в UTC.

```text
  users                    transactions                  categories
+---------+              +---------------+              +------------+
| id (PK) | <----+       | id (PK)       |       +----> | id (PK)    |
| email   |      +------ | user_id (FK)  |       |      | name       |
| role    |              | category_id   | ------+      | color      |
+---------+              | amount        |              +------------+
                         | created_at    |
                         +---------------+
```

### 2.2. Зачем нужны миграции Flyway (Почему нельзя менять базу руками)
Когда вы разрабатываете проект один, возникает соблазн открыть pgAdmin или DBeaver и вручную нажать «Добавить колонку». 

**Почему в реальной разработке это запрещено:**
Когда вы задеплоите бэкенд на облачный сервер, там будет пустая база данных. Если вы меняли структуру руками у себя на ноутбуке, облачный бэкенд сразу упадет с ошибкой `column not found`.

**Как решает проблему Flyway:**
Все изменения структуры базы пишутся в виде SQL-файлов версий в папке `src/main/resources/db/migration/`:
* `V1__create_users_table.sql`
* `V2__create_transactions_table.sql`
* `V3__add_currency_to_users.sql`

При каждом старте Spring Boot проверяет историю: какие скрипты уже выполнялись, а какие новые. Flyway выполняет новые скрипты строго по порядку. Вся команда и продакшн-сервер всегда имеют гарантированно одинаковую структуру БД.

## 3. Бэкенд (Spring Boot 3): Мозг и правила бизнеса

Бэкенд на Java Spring Boot принимает запросы от фронтенда, проверяет права, выполняет расчеты и общается с PostgreSQL.

### 3.1. Классическая трехслойная архитектура
Код бэкенда разделен на три строгих слоя:

```text
HTTP Request ---> [ Controller ] ---> [ Service ] ---> [ Repository ] ---> PostgreSQL
                     Официант           Повар            Кладовщик
```

1. **Контроллер (`Controller`):**
   * Встречает входящий HTTP-запрос (GET, POST, PUT, DELETE).
   * Проверяет входные данные (`@Valid`): передан ли email, положительная ли сумма.
   * Не содержит никакой бизнес-логики! Его задача — принять запрос и отдать ответ.
   
2. **Сервис (`Service`):**
   * Содержит саму логику приложения.
   * Пример логики: «Проверить, не превышает ли расход текущий лимит пользователя. Если превышает — заблокировать операцию или отправить предупреждение».
   * Управляет транзакциями (`@Transactional`): если при переводе денег списание прошло, а зачисление упало с ошибкой — сервис откатит всю операцию назад, чтобы деньги не испарились.

3. **Репозиторий (`Repository`):**
   * Интерфейс Spring Data JPA (`JpaRepository`).
   * Превращает методы Java в чистый SQL-код:
     ```java
     // Вызов метода в Java:
     List<Transaction> findByUserIdOrderByCreatedAtDesc(Long userId);
     
     // Автоматически превращается в SQL:
     // SELECT * FROM transactions WHERE user_id = ? ORDER BY created_at DESC;
     ```

### 3.2. Безопасность: Аутентификация, JWT и Cookie

В вебе есть два разных понятия, которые новички часто путают:
* **Аутентификация:** «Кто ты такой?» (ввод логина и пароля, проверка, что ты это ты).
* **Авторизация:** «Что тебе разрешено делать?» (может ли обычный студент удалить чужую транзакцию? Нет, только свою. Может ли зайти в `/admin`? Нет).

#### Как работает безопасная сессия через JWT в HttpOnly Cookie:
1. Пользователь вводит email и пароль на фронтенде.
2. Бэкенд проверяет пароль с помощью алгоритма BCrypt (исходный пароль никогда не сохраняется в базу — только его математический односторонний хэш).
3. Если пароль верный, бэкенд генерирует **JWT (JSON Web Token)** — криптографически подписанную строку, внутри которой зашиты `userId` и `role`.
4. Бэкенд упаковывает JWT в заголовок ответа `Set-Cookie` с флагом **`HttpOnly`**.
5. **Почему именно HttpOnly Cookie, а не LocalStorage:**
   К cookie с флагом `HttpOnly` JavaScript браузера не имеет доступа. Если на сайт проникнет вредоносный скрипт (XSS-атака), он не сможет украсть токен пользователя. Браузер сам автоматически прикрепляет эту cookie к каждому запросу на бэкенд.

#### Вход через Google (OAuth 2.0):
Студенту не обязательно вводить пароль. Он нажимает «Войти через Google»:
1. Браузер перенаправляет пользователя на сервер Google.
2. Пользователь подтверждает доступ.
3. Google возвращает браузер назад на бэкенд с одноразовым проверочным кодом.
4. Бэкенд обменивает код у Google на email и имя пользователя.
5. Если такого пользователя еще нет в нашей базе, бэкенд автоматически создает ему аккаунт и выписывает нашу сессионную cookie.

## 4. Фронтенд (React 19 + TypeScript): Лицо приложения

Фронтенд запускается на компьютере или телефоне студента внутри браузера.

### 4.1. Архитектура Feature-Sliced Design (FSD)
Чтобы проект не превратился в свалку из сотен перепутанных файлов, мы используем стандарт FSD:
* `app/` — корневая инициализация приложения (роутер, темы, провайдеры).
* `pages/` — целые экраны приложения (DashboardPage, LoginPage, HistoryPage).
* `widgets/` — крупные самостоятельные блоки страницы (Header, BalanceCard, TransactionList).
* `features/` — конкретные действия пользователя (AddTransactionForm, FilterByDate, ExportReport).
* `entities/` — кирпичики предметной области (user, transaction, category).
* `shared/` — переиспользуемый фундамент (UI-кнопки, инпуты, API-клиент `base.ts`).

> **Правило направления зависимостей:** Верхние слои могут использовать нижние, но нижние НИКОГДА не могут импортировать верхние. `shared` ничего не знает о `features`, а `entities` ничего не знают о `pages`.

### 4.2. Как фронтенд запрашивает данные (TanStack React Query)
Вместо устаревшего ручного вызова `useEffect` для каждого чиха мы используем React Query:
1. Он автоматически кэширует ответы сервера.
2. Сам показывает индикаторы загрузки (`isLoading`) и ошибки (`isError`).
3. При добавлении нового расхода он инвалидирует кэш (`invalidateQueries(['transactions'])`), и список операций на экране обновляется мгновенно без перезагрузки всей страницы.

### 4.3. Three.js: Интерактивная 3D-сцена финансов
Вместо скучных плоских графиков в проекте используется 3D-визуализация:
* Библиотека Three.js создает WebGL-холст прямо в HTML.
* Финансовые потоки и баланс отображаются в виде интерактивной 3D-модели (например, парящие трехмерные кристаллы или денежные блоки).
* Высота или интенсивность свечения блоков привязана к реальным данным из базы: больше расходов — меняется геометрия или цвет.
* Это превращает учебный проект в презентабельный продукт уровня коммерческого стартапа.

## 5. Сквозной путь одного клика (Full-Stack Data Flow)

Давайте проследим, что происходит в системе за доли секунды, когда пользователь нажимает кнопку **«Добавить расход 50$ на Кофе»**:

```text
[ БРАУЗЕР: React 19 ]
  1. Пользователь заполнил форму и нажал "Сохранить".
  2. Валидация формы на клиенте: сумма > 0, категория выбрана.
  3. React Query вызывает функцию `transactionApi.create({ amount: 50, categoryId: 3 })`.
  4. Нативный `fetch` отправляет HTTP POST запрос на `http://localhost:8080/api/v1/transactions`.
  5. Браузер автоматически прикрепляет заголовок Cookie с токеном `MrDev_token`.

        |
        | [ СЕТЬ: Сетевой пакет HTTP JSON ]
        v

[ СЕРВЕР: Spring Boot 3 ]
  6. Фильтр безопасности `JwtAuthenticationFilter`:
     - Достает cookie `MrDev_token`.
     - Проверяет криптографическую подпись токена.
     - Узнает, что запрос пришел от пользователя с `userId = 42`.
  7. Контроллер `TransactionController`:
     - Принимает JSON и конвертирует его в Java DTO `CreateTransactionRequest`.
     - Проверяет аннотации `@NotNull`, `@Positive`.
  8. Сервис `TransactionService`:
     - Извлекает текущий баланс пользователя 42.
     - Проверяет бизнес-правила (например, дневной лимит).
     - Создает объект сущности `Transaction`.
  9. Репозиторий `TransactionRepository`:
     - Генерирует SQL-команду:
       INSERT INTO transactions (user_id, category_id, amount, created_at)
       VALUES (42, 3, 50.00, NOW());

        |
        | [ ДРАЙВЕР JDBC: TCP-соединение на порт 5432 ]
        v

[ БАЗА ДАННЫХ: PostgreSQL 17 ]
 10. База выполняет проверку внешних ключей (существует ли user 42 и category 3).
 11. Атомарно записывает строку на диск в файл таблицы `transactions`.
 12. Возвращает сгенерированный ID новой транзакции (например, `id = 105`).

        |
        | [ ОТВЕТ: HTTP 201 Created ]
        v

[ БРАУЗЕР: React 19 ]
 13. React получает успешный ответ с данными созданной транзакции.
 14. React Query сбрасывает старый кэш и запрашивает свежий баланс.
 15. Интерфейс перерисовывается: карточка расхода появляется в списке, а 3D-сцена Three.js плавно анимирует изменение баланса.
```

## 6. Топ-5 граблей начинающего Full-Stack разработчика

### Грабли 1: Ошибка CORS (Cross-Origin Resource Sharing)
* **Симптом:** В браузере красная ошибка: `Access to fetch has been blocked by CORS policy`.
* **Почему:** Фронтенд открыт на `http://localhost:5173`, а бэкенд запущен на `http://localhost:8080`. Браузер считает разные порты разными сайтами и блокирует запросы ради защиты от межсайтовых атак.
* **Решение:** На бэкенде в настройках Spring Security явно указать разрешенные источники (Origins):
  `allowed-origins: http://localhost:5173`. Либо на этапе разработки настроить proxy в `vite.config.ts`.

### Грабли 2: 401 Unauthorized против 403 Forbidden
* **401 Unauthorized:** Сервер не понял, кто вы. Вы либо не передали токен, либо срок действия сессии истек, либо токен поврежден. Решение: войти заново через логин.
* **403 Forbidden:** Сервер точно знает, кто вы, но вам сюда нельзя. Например, обычный студент пытается отправить запрос в эндпоинт `/api/v1/admin/courses`. Решение: проверить роли в токене.

### Грабли 3: Ошибка 500 Internal Server Error
* **Симптом:** Фронтенд просто показывает красный алерт: `500 Server Error`.
* **Ошибка новичка:** Начинать судорожно менять код фронтенда.
* **Правильное действие:** Ошибка 500 означает падение Java-кода на сервере. Нужно открыть терминал бэкенда и прочитать Stack Trace (первые строчки `Caused by:`). Там будет точная причина: упала ли база данных, произошел ли `NullPointerException` или нарушен уникальный индекс.

### Грабли 4: Рассинхронизация типов фронтенда и бэкенда
* **Симптом:** Бэкенд возвращает данные, но на экране отображается `undefined`.
* **Почему:** В Java поле назвали `createdAt`, а во фронтенде в TypeScript написали `created_date`.
* **Решение:** Всегда строго согласовывать DTO. Поля интерфейсов TypeScript в `entities/.../types.ts` обязаны буква в букву совпадать с полями Java DTO.

### Грабли 5: «Работает на моем компьютере, но не работает на сервере»
* **Почему:** Локально вы использовали адрес `http://localhost:8080`, пароль к базе `postgres` и хранили картинки на рабочем столе.
* **Решение:** Все конфигурации (адрес базы данных, секреты JWT, порты) должны передаваться через **переменные окружения (Environment Variables)**, а не зашиваться в код. В коде используются только плейсхолдеры `${DB_URL}` и `${JWT_SECRET}`.
